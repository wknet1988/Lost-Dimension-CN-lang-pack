## 一、已完成并验证的逆向成果

### 1.1 `.bra` 归档（已完全破解，解包/重打包均已验证）

`Data.bra` = 文本/数据归档（1.79 MB，1101 个文件）。小端。

```
归档头（16 字节）
  +0   "PDA\0"
  +4   u32 版本 = 2
  +8   u32 文件表偏移（绝对文件偏移）
  +12  u32 文件数

数据区（从 16 开始，每个文件一块）
  +0   u32 解压后大小
  +4   u32 压缩后大小（不含这 16 字节头）
  +8   u32 CRC32(解压后数据)
  +12  u32 标志
  +16  raw deflate 数据（zlib wbits = -15）

文件表
  每项：u32 hash1, u32 hash2, u32 压缩总长(=16+压缩后), u32 解压后大小,
        u16 名称字段长(4 字节对齐, 含 \0), u16 0x20, u32 数据偏移, char[名]
  名称形如 Font\Font18.tpc.GL.phyre（**不带 Data\ 前缀**，Data 是游戏内数据根）
```

**验证结果**
- 解包 1101 个文件，CRC 全部通过
- 用原文件表（保留 hash1/hash2/对齐）重建归档 → 再解包 → **1101/1101 文件字节级一致**
- 修改单个文件后重建，只有该文件内容变化，其余 1100 个文件字节不变

## 二、关于「挂载外部中文字体」的结论

### 2.1 运行时挂载 .ttf / .otf —— **不可行**

证据（全部来自本机文件实测，非推测）：

1. `LostDimension.exe`（7.65 MB, PE32, ImageBase 0x400000）中搜索 `FreeType`、`FT_Init`、`.ttf`、`.otf`、`.fnt`、`glyph` —— **命中数全部为 0**。
2. 引擎字体相关的全部 RTTI 类名只有这些（Phyre 的 AL 抽象层）：

   ```
   ALFontManager   ALFont   ALFontImp   ALFontChildImp
   ALFontCodeConv  AL8BitFontCodeConv  ALSJisFontCodeConv  ALTableFontCodeConv
   ALCompressFontImp  ALExpandFontImp
   ALTextImp  ALTextDraw  ALTextLetterSpacingPropImp  ALTextLineHeightPropImp ...
   ```
   没有任何 TrueType/矢量字形相关类。
3. exe 内引用的字体资源路径只有 6 条，全部是位图贴图：

   ```
   Font/Font18.tpc.phyre      Font/Font22.tpc.phyre
   Font/FontWis1.tpc.phyre    Font/FontWis2.tpc.phyre
   Font/FontWis3.tpc.phyre    Font/FontWisTelop.tpc.phyre
   ```
4. 归档内 `Data/Font/` 只有 6 个 `.phyre` + `Data/DebugFont/debugfont.GL.phyre`，**没有任何字形度量表/码表文件**（`Data/Table/` 20 个子目录全是游戏数据表）。

> 要"运行时挂载 TTF"，等于写一个 DLL 注入 + 自己接管 GL 文本绘制（整条文本渲染链重写），工程量远超汉化本身，不推荐。

### 2.2 构建期「用外部 TTF 烘焙成 .phyre 图集」—— **可行，已跑通**

这是「挂载外部字体」在工程上唯一现实的等价物：**字体源用外部 TTF，产物仍是引擎认识的 A8 位图图集**。

已实现并验证的工具（`work/tools/ld_font.py`）：

| 能力 | 状态 |
|---|---|
| 从 `.phyre` 提取 A8 图集 | ✅ |
| 写回 `.phyre`（同尺寸，头部一字不动） | ✅ 验证：文件长度不变，仅像素区变化 |
| 用 TTF 按游戏网格烘焙指定字符 | ✅ |
| 量化到 16 级 alpha（与原生图集一致） | ✅ |
| 端到端：改图集 → 重打包 → 再解包校验 | ✅ 仅 4639 字节变化，全部落在像素区（2790–1051365），其余 1100 文件字节不变 |

### 2.3 字体图集的真实情况（本轮新发现，关键）

| 项 | Font18 | Font22 |
|---|---|---|
| 文件大小 | 1,051,366 B | 2,100,068 B |
| 头部长度 | 2,790 B | 2,916 B |
| 图集 | 1024×1024 **A8**（1 字节/像素） | **两页** 1024×1024 A8（2916 + 2×1048576） |
| 灰度级 | 仅 16 级（0,17,34,…,255）→ 源头是 4bit alpha 扩展 | 同 |
| 存储方向 | **上下翻转**（GL 纹理惯例），字形在图集「下方」存储 | 同 |

**字形网格（实测，自相关周期 ≈21.8）**
- 格距 **22×22 px**，首格原点约 **(30, 1)**（翻转后的坐标）
- 每行 **45 列**，当前只用了 **8 行**（≈360 个字形）
- 每页理论可容纳 **45 × 47 ≈ 2115** 格，**空闲约 1700 格/页**；Font22 有两页

**图集内容**
- 前 8 行：`? 0-9 A-Z` → 小写 → **平假名** → **片假名** → 半角/符号区
- 也就是说：**这是日文版的 SJIS 字库，被英化版直接复用了**；假名按 Shift-JIS 顺序排列，但 **一个汉字都没有**（英化时把汉字字形裁掉了）
- 结论：图集空间其实够用（约 1700 空槽/页），**真正的瓶颈不在图集，而在 exe 的码位解析**。

### 2.4 真正的拦路虎：码位空间

- 文本是 **16 位/字符**（这一点对中文有利，天然支持 2 字节码）
- 但现有英文只用到 `0x00E0–0x01FF` 这 **288 个码位**（值 − 0xE9 = ASCII）
- 图集按"字形顺序"紧密排布，而**图集顺序不等于码位顺序**（首字形是 `?`，但 `?` 的码位比数字大），说明存在一份"码位 → 槽位"的映射，且它**不在任何归档文件里**，只能编译进了 exe（`ALTableFontCodeConv` / `AL8BitFontCodeConv` 之一）

→ 要放 3000+ 汉字，必须让引擎能寻址到 3000+ 个槽位。这一步绕不开改 exe 的字形查找逻辑。

## 一、pack.psarc 已完全解包（8179 个文件）

```
header(0x20)：'PSAR' | u32 ver=0x00010004 | 'zlib' | u32 toc_size(=数据区偏移 0x4d3c8)
              | u32 entry_size=30 | u32 entry_count=8179 | u32 block_size=0x10000 | u32 flags
TOC：30 字节/条；第 i 条的**解压后文件大小**位于 83 + 30*i（大端 u32）

解压流 = 纯文本文件清单(412073 B) + 各文件数据按 TOC 顺序首尾相接
→ 文件 i 的流内偏移 = 412073 + sum(sizes[0..i-1])
```

（.phyre→`PHYR`、.gtpc→`GTSF`、.aft→`ALFT`、.mbb/.tbb→`TBB2`、.psb→`PSB\0`）。

## 二、重大发现：`MiniGameFont.aft` = Unicode → 字形槽位映射表

`ALFT` 格式（小端）：

```
+0x00  'ALFT'
+0x04  ...（头部 24 字节，含字符集统计）
+0x18  条目数组，每条 6 字节：u16 字形槽位 | u16 Unicode 起 | u16 Unicode 止
```

实例（节选）：

| 槽位 | Unicode 范围 |
|---|---|
| 1 | あ (U+3042) |
| 6 | お..か (U+304A–U+304B) |
| 11 | ご..さ (U+3054–U+3055) |
| 105 | ！ (U+FF01) |
| 106 | ？ (U+FF1F) |

**这意味着引擎的字体系统是「Unicode 查表 → 字形槽位」机制，而不是硬编码 8 位码。**
对汉化是极大的利好：只要能提供一张含汉字的同类表 + 对应图集，理论上**不需要改 exe**。

> 注：目前只发现这一个 `.aft`（小游戏字体，107 个槽位）。主字体的同类表在 PS3 的
> `EBOOT.BIN`（`SCE\0` 加密，需解密）或 PC 的 `LostDimension.exe` 内，格式待定位。

# v4 更新：PC 文本编码已完全破解（2026-11-02 深夜）

## 6.1 关键突破：文本编码规则

上一版把 PC 文本误判为「需先找 ALFT 表」。实际上 PC 版的文本编码是**纯算术映射**，
不需要任何映射表：

```
TBB1 = 小端，TBB2 = 大端；字符串为 u16 数组，0x0000 结尾
code = ord(ch) + 0xC9        对 ch ∈ 0x20..0x7E（空格除外）
code = 0x00EB               空格（独立码位，覆盖上式）
code = 0x8001               换行
```

实测证据（`Table/Camp/CampTips.mbb` 原文）：

```
0x12e 0x126 0x8001 0x8001 0x11d 0x10e 0x11b 0x11b 0x118 0x11b 0x112 0x11c 0x11d 0xeb 0x10a ...
→ "e]"  \n \n  "TERRORIST" ATTACKS" CONTINUE:" The" world" ...
```

（0x12E−0xC9='e'，0x11D−0xC9='T'，0xEB=空格，0x8001=换行）

**字节级验证**：`TalkEvent06.mbb` 的 361 条串，`encode(decode(x)) == 原始 u16` 361/361；
全语料 7713 条 `decode(encode(x)) == x` 7713/7713。

## 6.3 字体图集几何（实测修正）

Font18 / Font22 均为 **A8、16 级灰度（0,17,…,255）、上下翻转存储**。
把图集翻正后统计「恒亮列/行」发现右 12 列与下 56 行是纯白填充，真实内容区为 **1012×968**：

```

```

首行内容（逐格目视）：

```

     "?"   空格   0-9      A-Z      a-h      i-z      あ い う え お か が ...
```

Font18 = 1 页（2024 槽，已用约 320，空闲约 1700）
Font22 = 2 页（4048 槽）
FontWis1/2/3 = 各 2 页，**页 0 是纯 ASCII 顺序排列，页 1 是整片纯白**（做遮罩用，无字形）

## 6.4 新的硬阻塞：码位 → 槽位 映射表

图集里字形顺序是 `? 空格 0-9 A-Z a-z 假名…`，而文本码位是 `ASCII+0xC9`，两者**不是线性关系**：

```
槽位:  ?=0  空格=1  0=2  9=11  A=12  Z=37  a=38  z=63
码位: 0x108  0xEB  0xF9 0x102 0x10A 0x123 0x12A 0x143
差:    0x108  0xEA  0xF7  0xF7  0xFE  0xFE  0x104 0x104
```

每段内差值是常数（0xF7 / 0xFE / 0x104），但段与段之间跳变 → 引擎内部有一张
「码位 → 字形槽」表，无法用公式代替。

**已排除的定位途径：**

| 途径 | 结果 |
|---|---|
| exe 里搜 `slot 12..37` / `code 0x10A..0x123`（LE+BE） | 0 命中 |
| exe 里搜 ASCII 字符序串 `"0123…ABC…abc…"` | 0 命中 |
| Font18/22 `.phyre` 头部 2790 字节 | 无该表（只有 RYHPT 对象表 + 纹理 chunk） |
| 全部 1101 个数据文件搜表片段 | 只有 3 处 shader 二进制误报 |
| `MiniGameFont.aft` 的 ALFT 表 | 只服务小游戏字体，槽位空间与主字体无关 |
| `Lua/*.bla`（384 个） | LuaQ 字节码，无字体逻辑 |

**根因**：`LostDimension.exe` 的 `.text` 段被 **SteamStub** 加密
（`.text` 熵 = 8.000，`.bind` 段 = 7.963），映射表编译在里面，静态不可读。

## 6.5 结论与后续两条路

文本层、打包层、字体烘焙层**全部打通且字节级验证通过**，唯一缺口是这张映射表。

- **路线 A（推荐）**：运行游戏后 dump 进程内存，从解密后的 `.text` 里取回映射表。
  拿到后即可把 2500 个常用汉字写进 Font22 的空闲槽（4048−已用 ≈ 3300，够用），

# 7. v5 更新：映射问题已解决，全链路跑通（结论推翻 6.4/6.5）

6.4 判断「映射表编译在加壳的 .text 里、静态不可读」是**错的**。真正的原因是
我一开始把字体图集的**格子尺寸搞错了**（用 22px，实际是 24px），导致槽位编号一路漂移，
于是怎么搜都对不上。改用正确的格子参数后，映射规则简单到不需要任何表。

## 7.1 决定性证据：debugfont

`Data/DebugFont/debugfont.GL.phyre` 只有 35557 字节，头部 2789，纹理 32768 = **128×256**。
按 8×16 的格子切分正好是 **16×16 = 256 格**，对应码位 0..255 —— 即
**码位就是槽位索引**（identity）。引擎的约定从此确定。

## 7.2 真正的图集几何（实测，自相关 + 内容边界）

对每页做列/行投影的自相关，峰值即格距；再用"最后一个非纯白行列"求内容边界：

| 字体 | 内容区 | 格距 | 列×行 | 槽/页 | 页数 |
|---|---|---|---|---|---|
| Font18 | 1012×968 | 22 | 46×44 | 2024 | 1 |
| Font22 | 1008×1008 | 24 | 42×42 | 1764 | 2 |
| FontWis1/2/3 | 1000×1000 | 12 | 83×83 | 6889 | 2 |
| FontWisTelop | 988×600 | 12 | 82×50 | 4100 | 1 |

> 早先误判 22px，是因为把 Font22 的格距当成了字号；22 是**字号**，24 才是**格距**。

## 7.3 映射规则

```
页内槽位 slot = code - 1
页     page = slot / (列数 × 行数)
像素   x = (slot % 列数) * 格距 ,  y = (slot / 列数) * 格距
```
槽位按**行优先**编号；图集按**自下而上**存储（读图时需 FLIP_TOP_BOTTOM）。

逐字验证（Font22 与 Font18 结果一致）：

| 字符 | 码位 | slot | 实际字形 |
|---|---|---|---|
| `!` | 0xEA | 233 | `!` ✓ |
| `0` | 0xF9 | 248 | `0` ✓ |
| `A` | 0x10A | 265 | `A` ✓ |
| `B` | 0x10B | 266 | `B` ✓ |
| `C` | 0x10C | 267 | `C` ✓ |
| `D` | 0x10D | 268 | `D` ✓ |
| `Z` | 0x123 | 290 | `Z` ✓ |
| `d` | 0x12D | 300 | `d` ✓ |
| `e` | 0x12E | 301 | `e` ✓ |
| `x` | 0x141 | 320 | `x` ✓ |

空格是特例：码位 `0xEB` → slot 234，而 234 在 Font22 里本来就是空白格，
所以空格能正常显示，代价是 `"`(0x22) 这个字符不可用（语料里也确实没出现过）。

## 7.4 归档 (.bra) 重建的三个坑

全部踩过并修好，缺一个就崩溃（弹 "Lost Dimension has stopped working"）：

1. **块头第 4 字段不是 0**。每个文件块的 16 字节头是
   `usize / compressedSize / crc32 / type`，type 取值为 `6` 或 `0x180006`。
   写成 0 会被引擎当成"未压缩"，直接崩。
2. **表项 h2 = 未压缩数据的 CRC32**，引擎会校验。改了文件必须同步重算。
3. **归档体积不能小于原始体积**。引擎按原尺寸 mmap，变小就越界读。
   解决办法：数据区零填充到原 `tab_off`（表仍在文件末尾）。

修好后：1101 个文件全量重打包、CRC 全部自洽、游戏正常进标题画面。

## 7.5 端到端验证（实机截图）

把 `汉` 用 msyh.ttc 烘焙到 **全部 6 个字体**的码位 `0x12E`（即字母 `e` 的位置），


同时用"把整页填白"的方式验证了**哪些文字是字体渲染的**：
